# LinkMesh 身份认证与密钥管理体系设计

> 状态：设计稿（P0 共享库基础已落地，P1/P2 待实施）
> 适用版本：protocol 帧头版本 1，协议能力版本 2（`PROTOCOL_VER = 2`）

本设计为 LinkMesh（NAT 穿透 VPN）补充一套完整的**身份验证、密钥轮换、吊销**体系，
借鉴 Signal *Sealed Sender* 与 Matrix *Cross-Signing* 在去中心化与易用性之间的平衡思路，
并严格贴合现有代码结构（`linkmesh-shared` / `linkmesh-server` / `linkmesh-client`）。

---

## 1. 背景与现状

### 1.1 现有安全模型

- 每台设备本地生成 X25519 密钥对（`crypto.rs::generate_keypair`），私钥仅存本机配置文件；
- 信令通道：客户端 ↔ 服务端，负载用 `ECDH(客户端静态私钥, 服务端静态公钥)` 派生的共享密钥做
  ChaCha20-Poly1305 加密（`crypto.rs::shared_secret` + `encrypt/decrypt`）；
- 数据面：客户端 ↔ 客户端，同样用双方静态密钥的 ECDH 结果加密，服务端中继时**不解密**；
- 服务端公钥与网格根采用 **TOFU**（trust on first use）：`--join` 加入时一次性索取
  root 签名的 ServerInfo（KEYQUERY → `MSG_SERVERINFO`）并确认信任网格根指纹，
  之后每次连接比对服务器出示的公钥，不一致则拒绝（`connection.rs::ensure_server_pubkey`）；
  （历史明文 KEYRESP 通道已移除。）
- 路由表：`公钥 → 虚拟 IP → Endpoint`，任何人只要能发出可解析的封包即可注册、查询。

### 1.2 现有缺陷（威胁清单）

| # | 缺陷 | 后果 | 攻击示例 |
|---|------|------|----------|
| 1 | **无成员资格控制**：任何拥有密钥对的人都能注册任意虚拟 IP、查询任意对端 | 非授权入网；虚拟 IP 被抢占（`RouteTable::upsert` 甚至会把同 IP 的旧公钥条目顶掉，形成拒绝服务） | 攻击者注册受害者的 IP，所有发给受害者的查询都被路由到攻击者 |
| 2 | **中继头明文携带长期身份公钥且可伪造**：`RELAY` 头部的 `dest_pub/src_pub` 是静态身份密钥，服务器只按目标转发、不校验来源是否真的是该密钥的持有者 | 元数据泄露（线上可长期跟踪某设备的身份密钥）；向受害者定向投毒垃圾密文（解密失败但消耗资源） | 攻击者用受害者公钥作 `src` 给任意在线上目标发伪造中继帧 |
| 3 | **无密钥轮换**：静态密钥长期不变，数据面共享密钥也长期不变 | 无前向保密（PFS）：密钥一旦泄露，历史流量全部可解 | 窃取旧备份中的私钥，解密全部历史会话 |
| 4 | **无吊销机制**：设备丢失/泄密后没有任何系统性下线手段 | 被盗设备继续以合法身份入网 | 失窃笔记本上的 `client.json` 被直接使用 |
| 5 | **TOFU 仅一次**：首次接触无任何带外验证，且无法区分「服务器换了密钥」与「中间人」 | 首次连接可被 MITM | 在首次 `--connect` 时劫持 UDP 并给出自己的公钥 |
| 6 | **信令无重放防护**：nonce 随机、无计数器、无时间戳 | 重放旧信令可混淆路由表 | 重放受害者的注册/心跳包 |
| 7 | **信令/中继同密钥复用**：注册、查询、心跳共用同一共享密钥与同一随机 nonce 体系 | nonce 复用风险；消息类型间缺乏域分离 | — |

## 2. 设计目标与原则

### 2.1 从 Signal / Matrix 借鉴什么

- **Sealed Sender（Signal）**：收件人用一个短期、可轮换的地址接收消息，服务器只知道「谁在给谁路由」、
  不知道长期身份、更不知道内容。→ 我们引入**路由密钥（Routing Key, rk）**：数据面中继头部只携带
  短期路由密钥而非长期身份密钥；服务器按「已认证会话绑定的路由密钥」转发，杜绝头部伪造；
  中继内容保持端到端加密，服务器不可读。
- **Cross-Signing（Matrix）**：长期主密钥（master key）离线保管，签名各设备密钥与各种声明；
  设备密钥可安全轮换、可恢复、可跨设备验证。→ 我们引入**网格根密钥（mesh root）**：由管理员持有，
  签发设备证书、服务器信息、吊销列表；客户端只在**加入时一次性 TOFU 网格根指纹**，此后一切凭
  Ed25519 签名离线可验证——「信任一次，验证永远」。设备长期密钥轮换由旧密钥签名证明持有权，
  再由根密钥背书登记（Matrix 的「主密钥签名新设备密钥」同构）。
- **两者的共同点**：把「易用性」建立在**单一、低频、可带外确认的信任锚**上，把「去中心化/健壮性」
  建立在**可离线验证的签名链**上。我们完全采用这一结构：`mesh root → 设备证书 / CRL / 轮换声明`。

### 2.2 设计原则

1. **信任一次，验证永远**：唯一需要人工确认的动作是加入时确认网格根指纹（显示分组 base32 指纹，
   支持 `-y/-n`）；之后所有身份/轮换/吊销信息均可由签名链离线验证。
2. **私钥不迁移、不共享**：设备私钥、根私钥都只存在于本机；轮换是「生成新钥 + 签名声明 + 吊销旧钥」，
   绝不传输私钥。
3. **前向保密（PFS）**：会话密钥必须含临时密钥成分，且临时密钥与已退役会话密钥**用后即清零**；
   单一静态密钥泄露不能解出历史会话。
4. **最小元数据**：线上（信令/中继头部）尽量只出现短期密钥；长期身份仅出现在握手负载内。
5. **默认拒绝**：未认证会话不能注册、查询、中继；吊销立即在服务端强制生效，客户端同步为纵深防御。
6. **诚实界定去中心化**：v1 采用「单一网格根」（适合单运营者网格，如同 SSH CA），
   但所有结构（签名声明、证书、CRL）都是可组合的，为多根/联邦留出扩展位（见 §10.4）。

## 3. 信任模型与密钥层次

### 3.1 密钥种类总览

| 密钥 | 算法 | 生命周期 | 用途 | 存放 |
|------|------|----------|------|------|
| 网格根 `root` | Ed25519 | 长期（离线保管） | 签发设备证书、ServerInfo、CRL、轮换声明 | `mesh.json`（chmod 600），离线备份/恢复口令 |
| 服务端加密密钥 `ik_x_s` | X25519 | 长期（可轮换） | 信令握手 ECDH | `server.json` |
| 服务端签名密钥 `ik_s_s` | Ed25519 | 长期（与 root 轮换节奏一致） | 会话 Rekey 签名等 | `server.json` |
| 设备加密密钥 `ik_x` | X25519 | 长期（可轮换） | 握手 ECDH、数据面静态成分 | `client.json` |
| 设备签名密钥 `ik_s` | Ed25519 | 长期（可轮换） | 证书绑定、轮换/重协商签名 | `client.json` |
| 会话临时密钥 `ek_c` / `ek_s` | X25519 | 每次连接生成，用后清零 | 3-DH 会话密钥派生（PFS） | 内存 |
| 路由密钥 `rk` | X25519 | 每次连接/重协商生成 | 数据面中继寻址与数据面密钥派生 | 内存 |
| 会话密钥 `SK` | HKDF 输出 | 一次连接或一个轮换周期 | 信令/数据 AEAD | 内存（`SessionKey`，Drop 清零） |

### 3.2 设备身份与设备 ID

设备身份 = **双长期密钥**：

```
ik_x  : X25519 公钥（与现有 wire 格式完全兼容）
ik_s  : Ed25519 公钥（新增；X25519 无法签名，故引入）
device_id = SHA-256("linkmesh-device-v1" ‖ ik_x ‖ ik_s)[0..32]
```

- `device_id` 是目录、证书、CRL、轮换声明中使用的**稳定标识**（base64，43 字符），
  由 `identity.rs::device_id()` 计算；
- 展示用**指纹**取 `device_id` 前 20 字节做 base32，4 字符一组（SSH 风格，共 32 字符）：
  `ABCD EFGH IJKL MNOP QRST UVWX YZAB CDEF`，由 `identity.rs::fingerprint()` 生成，
  在加入、验对端、吊销时人工比对。

### 3.3 网格根与签名链

```
                    ┌──────────────── mesh root (Ed25519, 离线) ────────────────┐
                    │ 签发                                                  │
                    ▼                                                       ▼
        DeviceCert（设备证书）                          Crl（吊销列表）/ ServerKeyStatement / RotationStatement
   device_id + ik_x + ik_s + allowed_ip + 有效期               version 单调递增，root 签名
```

- **设备证书 `DeviceCert`**：把「设备身份（双公钥）→ 虚拟 IP + 有效期」绑定为一条可离线验证的声明；
- **服务器信息 `ServerInfo`**：把「网格根公钥 + 当前服务器双公钥 + CRL 版本 + 协议版本」绑定，
  由 root 签名，客户端据此一次性 TOFU 根指纹并固定服务器公钥；
- **吊销列表 `Crl`**：`{ version, entries[{device_id, reason, revoked_at, replacement}] }`，
  root 签名，version 单调递增；
- **轮换声明**：`RotationStatement`（旧设备密钥签名 + root 签名）、`ServerKeyStatement`（root 签名）。

客户端对任何声明的验证链都是 `root 公钥（已固定）→ 签名 → 声明内容`，可完全离线完成。

### 3.4 与 Matrix Cross-Signing 的对应

| Matrix | LinkMesh |
|--------|----------|
| Master Signing Key | 网格根 `root`（离线保管，支持恢复口令备份） |
| 主密钥签名设备签名密钥 | root 签发 DeviceCert（绑定 ik_x + ik_s） |
| 设备 ID（device_id） | 由 ik_x + ik_s 推导的稳定标识 |
| 设备密钥轮换由主密钥背书 | RotationStatement 由 root 签名背书 |
| 设备丢失 → 重置/吊销 | CRL + 重新加入 |

## 4. 身份验证

### 4.1 加入（onboarding）

取代现有「裸 TOFU `--connect`」：

1. 管理员初始化网格：`linkmesh-server --mesh-init` 生成 `mesh.json`（root 私钥 + 空 CRL），
   显示网格根指纹；建议 `--backup-mesh` 加密备份。
2. 管理员签发加入码：`linkmesh-server --invite [--ip 10.13.13.50]` → 输出一次性加入码
   `LMJ-XXXX-...`（128 bit 随机，服务端只存哈希，10 分钟过期、单次有效，可预绑定虚拟 IP）。
3. 设备侧：`linkmesh-client --genkey`（现在同时生成 ik_x + ik_s），然后
   `linkmesh-client --join "<server:port>" "<vmnic>" --code LMJ-... [-y|-n]`：
   a. 向服务器索取 `ServerInfo`（KEYQUERY 的新响应，见 §7），**校验 root 签名**，
      显示网格根指纹，`-y` 确认信任（或带外比对）→ 客户端固定 `mesh_root_pub` 与服务器公钥；
   b. 发送 `MSG_JOIN`：`{ code, device_id, ik_x, ik_s_pub, requested_ip }`，
      负载用 `ECDH(ik_x_c, ik_x_s)` 加密（与现有信令一致）；
   c. 服务端校验加入码 → 分配虚拟 IP（加入码预绑定优先，否则从池中分配）→
      签发 `DeviceCert` 并返回；
   d. 客户端把 `mesh_root_pub`、`DeviceCert` 写入该服务器条目。
4. **离线/带外模式**：管理员拿到设备公钥后执行 `linkmesh-server --issue "<ik_x>" [--ip ...]`
   直接签发证书（类似 `authorized_keys` 工作流），设备再用
   `--join` 的 `--no-code` 变体完成绑定。两种方式都保证**只有证书持有者能入网**。

### 4.2 会话认证握手（每次连接）

```
C ── AUTH(header: ik_x_c; 负载: AEAD(ECDH(ik_x_c, ik_x_s)) { AuthBody }) ──▶ S
    AuthBody = { device_id, cert: DeviceCert, ek_c(新临时公钥), timestamp, nonce(12B) }

S 校验：cert 签名(root) ✔  device_id 与 cert/ik_x 一致 ✔  未过期 ✔  未吊销(CRL) ✔
         timestamp 在 ±30s 内 ✔  nonce 未在重放缓存中 ✔
S ── AUTH_RESP(负载: AEAD(会话密钥 SK) { AuthRespBody }) ──▶ C
    AuthRespBody = { ek_s(服务端临时公钥), session_id, crl(当前 CRL), server_info, allocated_ip }

SK = HKDF-SHA256(
      salt  = nonce,
      ikm   = DH(ek_c, ik_x_s) ‖ DH(ik_x_c, ek_s) ‖ DH(ek_c, ek_s),   // 3-DH
      info  = "linkmesh/session/v1",
      len   = 32)
```

- 3-DH 由双方各自计算（`crypto.rs::derive_session_key_client/server`），结果一致；
- **前向保密**：SK 含双方临时密钥成分；连接结束后临时密钥与 SK 清零（`SessionKey` Drop 时擦除），
  仅静态密钥泄露无法恢复历史 SK（§10.2 详细论证）；
- 握手后所有信令帧头部携带 `session_pub = ek_c`，负载用 SK + **递增计数器 nonce** 加密（§7.1），
  服务端据此防重放并建立 `session_pub → device_id → 虚拟 IP → endpoint` 映射；
- 握手响应顺带下发当前 CRL，客户端本地缓存 `crl_version`，之后按需增量拉取。

### 4.3 虚拟 IP 分配与防伪造

- 虚拟 IP 由服务端**分配**（`--invite --ip` 预绑定或池内分配），写入 DeviceCert 的 `allowed_ip`；
- 注册/心跳时客户端上报的 IP 必须与证书一致，否则拒绝 —— 从根上消灭 IP 抢占（缺陷 #1）；
- 现有 `RouteTable::upsert` 的「同 IP 不同公钥互相顶替」逻辑保留但只对**同一设备 ID** 生效。

### 4.4 服务端强制（ACL / 重放 / 限速）

- **默认拒绝**：未通过 AUTH 的会话不能 REGISTER / QUERY / RELAY / NOTIFY；
- **重放缓存**：每设备最近 nonce 环形缓存 + timestamp 窗，重复即丢弃；
- **限速**：对 AUTH/JOIN 按源 IP 令牌桶限速（P1 落地），防枚举与刷码；
- **会话与路由绑定**：中继转发只接受「来源路由密钥属于某个已认证会话」的帧（P2 落地 rk 头部后）。

## 5. 密钥轮换

### 5.1 会话级自动轮换（PFS，频繁）

- **信令会话**：默认每 30 分钟或服务器重启后双方重协商：任一方发 `MSG_REKEY`
  `{ new_ek, timestamp, signature(ik_s 签名) }`（负载用当前 SK 加密），双方以
  `HKDF(旧 SK ‖ 新 DH 组合, "linkmesh/session/v2")` 派生新 SK，旧 SK 清零；
- **数据面对端会话**：默认每 15 分钟或 1 GiB 轮换路由密钥 rk：`Rekey` 消息（AEAD 当前对端密钥 +
  ik_s 签名，含新 rk 公钥与 epoch 号）；新对端密钥 =
  `HKDF(DH(ik_x_c, ik_x_p) ‖ DH(rk_c, rk_p), "linkmesh/peer/v1")`，旧密钥清零；
- 隧道帧内增加 `epoch(4B) ‖ seq(8B)` 前缀，接收端拒绝过期 epoch 与乱序 seq（§7.1）。

### 5.2 设备长期密钥轮换（合作式，低频）

`linkmesh-client --rotate-key`（设备仍持有旧私钥、怀疑泄露或例行更换）：

1. 本地生成新 ik_x/ik_s → 新 device_id；
2. 在当前会话内发送 `MSG_ROTATE`：
   `RotationStatement { mesh_id, old_device_id, new_device_id, new_ik_x, new_ik_s_pub, timestamp,
                         old_key_signature(旧 ik_s 签名), root_signature }`；
3. 服务端校验：旧设备证书有效 ✔ 旧 ik_s 签名有效（证明持有旧私钥）✔ 非吊销 ✔
   → 签发新 DeviceCert、把旧 device_id 加入 CRL（reason=`Rotated`，replacement=新 id）、
   广播轮换通知给在线成员；
4. 客户端更新本地配置（保留旧 ik 的备份用于追溯，不再使用）。

### 5.3 服务端密钥轮换

`linkmesh-server --rotate-server-key`：

- 生成新 ik_x_s/ik_s_s，由 root 签发 `ServerKeyStatement { mesh_id, old_server_ik_x, new_ik_x, new_ik_s_pub, timestamp }`；
- 客户端收到后校验：root 签名 ✔ 且 `old_server_ik_x` 等于本地固定的服务器公钥 ✔ → 自动更新固定值，
  **无需人工干预**（这正是固定 root 而非服务器公钥的意义）；
- 旧服务器公钥加入 CRL（reason=`Rotated`）防回退。

### 5.4 网格根密钥轮换（灾难恢复）

root 泄露是网格的「末日场景」，不存在更高权威：流程为

1. 带外发布「旧根指纹失信」通知（所有成员人工确认，等价于一次重新加入）；
2. 新生成 root，全体设备**重新加入**（`--join` 新码）重新签发证书；
3. 旧 CRL 作废。建议通过 `--backup-mesh` 加密备份 + 恢复口令（Matrix recovery key 思路）降低该场景概率。

## 6. 吊销机制

### 6.1 CRL 结构

```
Crl { mesh_id, version(u64, 单调递增), entries: [ { device_id, reason, revoked_at, replacement? } ], signature }
reason ∈ { Compromised, Leaked, Rotated, Admin, Discontinued }
```

- 由 root 签名（`cert.rs::Crl::sign/verify`），任何客户端可离线验证；
- 客户端缓存最新 `crl_version`，仅接受版本更新的 CRL（防回退降级攻击）。

### 6.2 吊销传播（推 + 拉）

- **触发**：`linkmesh-server --revoke <device_id|ik_x> [--reason compromised|...]`
  → 服务端用 root 签名 CRL v+1 → **立即踢掉该设备全部活动会话**（`MSG_KICK` + 路由表删除）；
- **推送**：向在线成员广播 `MSG_CRL_NOTIFY`（各会话 SK 加密），成员即时更新本地 CRL 并断开与
  被吊销设备的对端会话；
- **拉取**：离线成员下次 AUTH 时在握手响应中收到最新 CRL；另有 `linkmesh-client --check`
  手动同步；默认 CRL 刷新间隔 10 分钟（可配）。

### 6.3 强制下线与会话终止

吊销在**服务端立即生效**（拒绝 AUTH、踢会话、删路由、禁中继），因此即使某对端尚未同步 CRL，
被吊销设备也无法再借服务器入网；对端侧 CRL 同步是**纯直连（打洞成功）场景的纵深防御**：
吊销到对端同步之间存在有界窗口（≤ CRL 刷新间隔），见 §10.2 取舍说明。

### 6.4 重新入网

被吊销设备重新入网 = 生成全新密钥 → 管理员发新加入码/`--issue` 新公钥 → `--join`。
旧 device_id 永久留在 CRL（含 reason=Rotated 时指向 replacement），防止旧钥复用。

## 7. 协议改动

### 7.1 帧格式

**信令帧**（保持现有布局，仅语义变化）：

```text
0-1   magic             "LM"（不变）
2     version           帧头版本 1（不变）；协议能力版本见 ServerInfo.auth_required
3     msg_type          （新增类型见下）
4-35  sender_public_key 握手期 = ik_x_c；会话建立后 = session_pub(ek_c)
36..  ciphertext        握手期 = nonce(12B 随机)+ChaCha20-Poly1305(ECDH(ik) 密钥)
                       会话期 = counter(8B BE)+role(1B)+ChaCha20-Poly1305(SK)   ← 确定性 nonce，防重放
```

**中继帧（P2 迁移，目标形态）**：

```text
0-1   magic      "LM"
2     version    1
3     msg_type   RELAY / RELAY_BATCH（不变）
4-35  dest_rk    目标路由密钥（短期，代替长期身份密钥）
36-67 src_rk     来源路由密钥（短期）
68..  ciphertext epoch(4B)+seq(8B) + 对端会话密钥 AEAD 密文
```

服务器按 `rk → 已认证会话 → device_id → endpoint` 转发；来源 rk 未绑定已认证会话即丢弃。
P1 过渡期保持现有 ik_x 头部但服务端强制成员校验，P2 再切 rk。

### 7.2 新消息类型（`protocol.rs` 常量）

| 常量 | 值 | 方向 | 说明 |
|------|----|------|------|
| `MSG_SERVERINFO` | 0x0B | S→C | 签名 ServerInfo（KEYQUERY 的响应） |
| `MSG_JOIN` | 0x0C | C→S | 加入请求（加入码 + 设备双公钥） |
| `MSG_AUTH` | 0x0D | C→S | 会话认证（证书 + 临时公钥） |
| `MSG_AUTH_RESP` | 0x0E | S→C | 认证响应（服务端临时公钥 + CRL + 分配 IP） |
| `MSG_REKEY` | 0x0F | 双向 | 会话/路由密钥轮换 |
| `MSG_ROTATE` | 0x10 | C→S | 设备长期密钥轮换声明 |
| `MSG_CRL` | 0x11 | S→C | 拉取/下发 CRL |
| `MSG_CRL_NOTIFY` | 0x12 | S→C | CRL 更新推送 |
| `MSG_KICK` | 0x13 | S→C | 会话被吊销/强制下线 |

`PROTOCOL_VER = 2` 由 ServerInfo 声明；帧头 `VERSION` 恒为 2（旧版 v1 明文客户端已不再兼容）。

### 7.3 信令负载（JSON，均在 AEAD 内）

```jsonc
// AuthBody（C→S, MSG_AUTH）
{ "device_id": "…b64…", "cert": { /* DeviceCert */ },
  "ek_c": "…b64…", "timestamp": 1710000000, "nonce": "…b64 12B…" }

// AuthRespBody（S→C, MSG_AUTH_RESP）
{ "ek_s": "…b64…", "session_id": "…b64 16B…", "allocated_ip": "10.13.13.50",
  "crl": { /* Crl */ }, "server_info": { /* ServerInfo */ } }

// JoinBody（C→S, MSG_JOIN）
{ "code": "LMJ-…", "device_id": "…", "ik_x": "…b64…", "ik_s_pub": "…b64…",
  "requested_ip": "10.13.13.50" }
```

## 10. 安全论证与已知取舍

### 10.1 攻击面对照表（缺陷 #1–#7 的消解）

| 威胁 | 消解机制 | 关键代码点 |
|------|----------|-----------|
| 非授权入网 / IP 抢占 | 设备证书 + 服务端分配 IP + 默认拒绝 | `cert.rs::DeviceCert`、§4.3 |
| 中继头伪造 / 身份元数据 | 会话绑定路由密钥（P2 后头部仅短期密钥） | §7.1、`signaling.rs` 会话表 |
| 无前向保密 | 3-DH 会话密钥 + 用后清零 + 自动 Rekey | `crypto.rs::derive_session_key_*`、`SessionKey` |
| 无吊销 | CRL（root 签名、版本单调）+ 强制踢会话 + 推拉同步 | `cert.rs::Crl`、§6 |
| 首次接触 MITM | 加入时固定 root 指纹，ServerInfo 签名验证 | §4.1、§4.2 |
| 信令重放 | 时间戳窗 + nonce 缓存 + 会话期计数器 nonce | §4.2、§7.1 |
| 密钥域混用 | 每类声明独立规范化前缀（`linkmesh-*-v1`）+ HKDF info 域分离 | `cert.rs::canonical` |

### 10.2 诚实局限

1. **元数据**：服务器仍可见「哪个会话在何时与谁通信、流量大小/节奏」—— 与 Sealed Sender 的完全匿名
   不同，这是「服务器即网格运营者」模型的固有属性；我们消解的是**长期身份关联**与**内容可见性**。
2. **被攻陷服务器**：恶意服务器可拒绝服务、篡改目录、作伪 CRL；客户端侧用 root 签名 + 对端交叉验证
   （P3）缓解，但无法根治（单点信任锚）。
3. **吊销窗口**：纯直连会话中，对端 CRL 同步存在 ≤ 刷新间隔的窗口；服务端强制踢会话已封堵借服务器
   入网的路径，窗口仅影响已打洞的直连。可配 `crl_refresh_sec` 折衷。
4. **DoS**：UDP 无连接，垃圾包洪泛只能靠限速/丢弃缓解；对端端口垃圾包在 AEAD 层被静默丢弃（现状不变）。
5. **静态密钥双泄露**：若同一设备的 ik_x 私钥与服务器 ik_x 私钥同时泄露且攻击者记录了握手期临时公钥，
   历史会话可被恢复（X3DH 同款性质）；缓解 = 更频繁的长期密钥轮换与根密钥离线保管。

### 10.3 密码学注意事项

- **nonce 纪律**：握手期随机 nonce + 时间戳；会话期 8 字节计数器（单调、不归零）+ 1 字节方向位 +
  3 字节零填充组成 12 字节 nonce，杜绝复用；
- **HKDF 域分离**：会话/对端/轮换派生使用不同 info（`linkmesh/session/v1`、`linkmesh/peer/v1`…）；
- **零化**：临时密钥与已退役 SK 必须清零（`SessionKey` Drop 实现），这是 PFS 论证的前提；
- **规范化签名输入**：声明签名使用固定字段序的 `k=v` 行（`cert.rs::canonical`），不依赖 serde
  序列化顺序，防跨实现签名不匹配。

### 10.4 去中心化扩展位

单一网格根是 v1 的易用性选择；签名声明结构使其可扩展为：多根联邦（root 间互签背书）、
成员自治（用户级 MSK 签名自己的设备，root 只做目录登记，即完整 Matrix cross-signing 形态）、
以及服务器间目录同步（跨网网格）。这些都不改变客户端验证模型（固定根 → 验证签名链）。
